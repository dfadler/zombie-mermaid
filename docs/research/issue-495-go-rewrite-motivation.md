# Research: motivation check for #495 (Go core rewrite)

🤖 **Claude:** This document was produced by an AI assistant investigating
[issue #495](https://github.com/dfadler/zombie-mermaid/issues/495) at
@dfadler's request, as part of an oldest-first backlog sweep. It answers the
issue's own explicit gap ("the specific motivation ... hasn't been spelled
out yet") with measured data rather than assumption. This is scoping/research
only — no renderer code was changed, no Go was written, and no rewrite was
started.

## Summary

The evidence does not support proceeding with a Go-core rewrite. Both of the
issue's own flagged risks turn out to be real, hard constraints rather than
open questions:

- **Bundle size would very likely regress**, not improve, for the SVG entry
  point, and would almost certainly regress for the ASCII-only entry point,
  which today deliberately avoids paying any layout-engine cost at all.
- **Synchronous rendering is genuinely load-bearing** (README, code, and
  `docs/react-integration.md` all confirm it), and a Go→WASM core cannot
  preserve it as an unconditional guarantee in the primary target
  environment (Chrome, and any main-thread browser context) once the
  compiled module exceeds a few KB — which any real parsing+layout core
  for six diagram types will.

Recommendation: **do not scope further implementation work.** Close or
downgrade #495 to "explored, not pursued" (mirroring #443's own
research-spike framing), citing this document. If a non-JS-host or
distribution motivation independent of bundle size/sync-rendering ever gets
articulated concretely, it would need to overcome both of the findings below
on its own merits — this document does not rule out _ever_ revisiting it,
only rules out proceeding on the motivation as currently (un)stated.

## 1. Bundle size

### Current TS+ELK.js bundle (measured, this branch)

Built via `pnpm run build` (`vite build --app --config vite.config.lib.ts`)
and measured via `pnpm run check:bundle-size`
(`scripts/check-bundle-size.ts`, gzip over `node:zlib`) on 2026-09-06:

| File                                           | Raw      | Gzip        | Budget (gzip) | Headroom |
| ---------------------------------------------- | -------- | ----------- | ------------- | -------- |
| `dist/index.js` (SVG + ASCII, ELK.js included) | 289.4 KB | **76.3 KB** | 110.0 KB      | −30.6%   |
| `dist/index.cjs`                               | 218.8 KB | 68.5 KB     | 110.0 KB      | −37.7%   |
| `dist/ascii.js` (ASCII-only, no ELK.js)        | 173.0 KB | **46.5 KB** | 65.0 KB       | −28.5%   |
| `dist/ascii.cjs`                               | 125.7 KB | 41.3 KB     | 65.0 KB       | −36.5%   |
| `dist/cli.js`                                  | 347.4 KB | 92.5 KB     | 116.0 KB      | −20.2%   |

All budgets are comfortably met today. These are the numbers a Go/WASM core
would need to beat (or at least approach) to be size-neutral, per the
README's own tracked, CI-enforced "Bundle Size" badge
(`badges/bundle-size.json`, generated by `scripts/generate-bundle-badge.ts`)
and the ASCII-only entry point's explicit reason to exist (skip ELK.js, "over
1.4MB minified", for a substantially smaller bundle — README, "Bundle Size"
and "ASCII Output" sections).

### Realistic Go→WASM comparison (web research, not measured — no Go build exists)

- **Standard Go compiler** is not a realistic option: a bare "hello world"
  Go→WASM build is already on the order of 2 MB raw (~1 MB+ gzip) before any
  actual application logic, because it embeds the full Go runtime/scheduler.
  This is off the table for a size-sensitive library. ([Why Your Go Binary
  Is Too Fat for WebAssembly](https://dev.to/alanwest/why-your-go-binary-is-too-fat-for-webassembly-and-how-tinygo-fixes-it-24l))
- **TinyGo** (the realistic alternative compiler) gets a trivial "hello
  world" down to hundreds of bytes to a few KB, but real, non-trivial
  programs land "~200 KB to 2 MB depending on mode" raw
  ([Zero-Friction Demos with WASM](https://kmcd.dev/posts/wasm-demos/);
  [TinyGo binary size optimization guide](https://tinygo.org/docs/guides/optimizing-binaries/)).
  Gzip compresses WASM well in practice (one documented case: 2 MB → 0.5 MB,
  a 75% reduction — [Minimizing Go WebAssembly Binary Size](https://dev.bitolog.com/minimizing-go-webassembly-binary-size/)),
  but even generously applying that ratio to the low end of TinyGo's real-
  program range (200 KB raw) lands around 50-70 KB gzip — before adding the
  JS-side glue/wrapper code every WASM package still needs (TinyGo's own JS
  runtime shim, marshalling, the idiomatic TS wrapper the issue itself
  requires).
- **A closer analog than "hello world": `yoga-layout`**, a real, shipped
  npm package wrapping a C++ layout engine as WASM (conceptually the same
  shape #495 proposes: native layout core, WASM target, JS-idiomatic
  wrapper). Its modern package is reported around **45 KB gzip**
  ([HN comment on yoga-layout bundle size](https://news.ycombinator.com/item?id=20480340)),
  while an older prebuilt variant (`yoga-layout-prebuilt`) added roughly
  **600 KB gzipped** to a webpack bundle
  ([react-pdf issue #619](https://github.com/diegomura/react-pdf/issues/619)).
  That 45 KB–600 KB spread for "a layout engine as WASM" in practice is the
  single most relevant comparison point available, and it straddles both
  sides of zombie-mermaid's current 46.5 KB (ASCII) / 76.3 KB (SVG) gzip
  figures depending entirely on how carefully the WASM build is tuned —
  i.e., genuinely uncertain, not a clear win.

### Conclusion on bundle size

The issue's own placeholder ("a WASM binary is unlikely to be smaller than
the current TS+ELK.js bundle — needs measurement, not assumption") holds up
under actual research. Best case (a `yoga-layout`-grade, heavily-optimized
TinyGo build): roughly size-parity with today's SVG entry point, and a
regression for the ASCII-only entry point, which today pays zero layout-
engine cost and would instead need to embed a compiled Go binary (parser +
layout, six diagram types) that has no equivalent to "just don't import
ELK.js." Worst case (an unoptimized or standard-Go build): several times
larger. There is no plausible path to the ASCII entry point's current
44 KB-vs-just-parsing profile once a compiled binary — of any size — is
mandatory for every consumer, including ASCII-only ones, since Go/WASM
doesn't have code-splitting equivalent to "import a different subpath."

## 2. Synchronous rendering constraint

### Confirmed: sync rendering is load-bearing today, not incidental

- README: _"Synchronous rendering — No async, no flash. Works with React
  `useMemo()`"_ (Features list) and _"Rendering is **fully synchronous** —
  no `await`, no promises. The ELK.js layout engine runs synchronously via a
  FakeWorker bypass"_ (Quick Start).
- `docs/react-integration.md` states the mechanism explicitly: _"Because
  rendering is synchronous, you can call `renderMermaidSVG()` directly in
  the render body — no `useEffect` round trip, no flash,"_ and gives the
  `useMemo()`-wrapped pattern as the primary recommended integration, with a
  React-Compiler note that only the _manual_ `useMemo()` becomes redundant
  under the compiler — the synchronous, no-`useEffect` part "still matters
  either way." This confirms the issue's characterization precisely: sync
  rendering isn't just a nice-to-have, it's the property that makes
  calling the renderer directly in a component body (memoized or not)
  correct instead of requiring an effect + loading state.
- An async escape hatch already exists (`renderMermaidSVGAsync()`), so the
  library isn't sync-only by accident — sync is the deliberately chosen
  default path, async is the opt-in.

### Can a WASM core preserve this?

Two synchronous JS-side APIs exist for WASM: `new WebAssembly.Module(bytes)`
(compile) and `new WebAssembly.Instance(module, imports)` (instantiate). Both
are real, callable synchronously. But:

- **Chrome enforces a hard 4 KB cap on synchronous compilation on the main
  thread**: `WebAssembly.Compile is disallowed on the main thread` past 4 KB
  — this is a real `RangeError` in shipped Chrome, not a soft
  recommendation ([MDN, `WebAssembly.Module()`
  constructor](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WebAssembly/Module/Module);
  [webpack issue #6475, "Unable to import WebAssembly modules bigger than
  4KB"](https://github.com/webpack/webpack/issues/6475); [chromestatus
  entry tracking a proposed relaxation to
  8 MB](https://chromestatus.com/feature/5099433642950656)). Chrome has an
  open "Intent to Ship: Deprecate module size limit" proposal to raise this
  ([blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/nJw2zwaiJ2s/m/EYPgC5D3LwAJ)),
  so the ceiling may move, but as of this research it is not universally
  lifted across shipped browsers, and even the proposed 8 MB replacement is
  still a limit, not its removal.
- **Firefox and Safari don't share Chrome's 4 KB cap**, so behavior is
  browser-dependent today — a library can't rely on "synchronous compile
  always works," only "synchronous compile works in some browsers, for
  modules under some size, on the main thread."
- **A real Go/TinyGo core for six diagram types (parsing + layout) will
  exceed 4 KB by orders of magnitude** — per the bundle-size research above,
  realistic builds land in the tens-to-hundreds of KB raw. This isn't a
  corner case the library could stay under; it's guaranteed to blow the cap.
- **Node.js does not enforce this cap** (no browser main-thread/UI-blocking
  concern), so a Node-only consumer (the CLI, `zombie-mermaid/cli`,
  server-side rendering) could in principle keep synchronous WASM
  instantiation. But the library's primary stated use case for "sync
  rendering matters" is the **browser** React `useMemo()` pattern — exactly
  the environment where the cap bites.
- A common WASM-in-JS pattern sidesteps this by pre-instantiating the
  module once at module-load time (e.g., a top-level `await` or an
  async init the consuming app awaits before mounting), then exposing a
  synchronous _call_ into the already-instantiated module for each render.
  That does preserve "synchronous per-render call," but it does not
  preserve "synchronous end-to-end with no async step anywhere in the
  consumer's code" — it relocates the async boundary from "every render" to
  "once, at app startup," which is a smaller but still real, and still
  breaking, change to the public API and the React integration pattern
  (an app using `useMemo()` today with no async setup would need to add
  one, or the library would need a top-level-await/auto-init pattern that
  doesn't compose cleanly with bundlers/SSR in general).

### Conclusion on synchronous rendering

The issue's characterization is correct and, if anything, understated: this
is not merely "could force a breaking API change," it is close to
unavoidable for a _main-thread-callable-with-zero-async-anywhere_ API once
the core is large enough to need WASM — which, per the size research above,
it will be. The best realistic outcome is "async once at startup, sync per
render," which is still a breaking change to the README's current contract
and to every existing `useMemo()`-based consumer's code (they'd need an
`await`/top-level-init step they don't have today).

## 3. Cross-reference with #443

[#443](https://github.com/dfadler/zombie-mermaid/issues/443) ("Research:
single-source, multi-language (Rust/Go) ASCII renderer with shared
conformance tests") is open, framed as an AI-assisted research spike, and
covers adjacent but distinct ground:

- #443 is scoped to the **ASCII renderer only** and is agnostic about
  whether TS compiles outward (to Rust/Go source, via a hypothetical
  TS-subset transpiler — its stated "no mature tool exists" direction 2) or
  a native Rust/Go core compiles outward to JS via WASM (direction 1, the
  same shape as #495). #495 is scoped to the **entire core** (all six
  diagram types, both SVG and ASCII) and commits specifically to a Go
  rewrite of the source of truth, not a TS-stays-canonical-with-alternate-
  targets model.
- #443 explicitly flags the same open question this document answers as
  unresolved: _"For the WASM-outward direction (Rust/Go core → JS via
  WASM), what would npm bundle size / cold-start cost look like in practice
  for this specific renderer, versus the current pure-TS implementation?"_
  — this document's bundle-size section is a direct, evidence-based answer
  to that open question (see §1), reusable by #443 as well as #495.
- #443 also raises, independently, whether there's _any actual user demand_
  for a Rust/Go native package at all ("No existing issue/discussion
  currently asks for one") — the same absence-of-demand concern applies to
  #495's motivation gap, and neither issue has since had that gap filled by
  a user request.
- No commits, branches, or PRs referencing "443" exist in this repository's
  history as of this research (`git log --oneline --all --grep=443`
  returned nothing), so there is no completed implementation or additional
  findings beyond the issue body itself to reconcile against.

Given the overlap, if #495 is closed or downgraded per this document's
recommendation, #443 should be revisited too — not necessarily closed
outright (it's framed as ASCII-only and open to the TS-stays-canonical
alternative, which doesn't carry the same bundle-size/sync-rendering
argument against it as cleanly, since it never proposed the TS source
stop being canonical), but its own "needs measurement" bundle-size question
is now answered and should be linked back to this document rather than
re-investigated from scratch.
